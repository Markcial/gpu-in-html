A page that reads itself

Every other example here hands the shader one rectangle. This one hands it forty-eight, and the browser decides where they go.

Scroll slowly. As each line of this paragraph rises past two thirds of the way up the window, a highlighter draws itself across it, left to right, and stops just past the last word. Not at the edge of the column — past the last word, wherever that happens to be on that particular line, at your particular window width, in your particular font.

None of the marks below are HTML. There is no element behind this text and no background on it. The paper, the fibre in the paper, the ink and the pen strokes in the margin are all a single fragment shader running on a canvas fixed behind the page, drawing at your display's refresh rate.

How it knows

The measurement is one browser API doing something it is rarely asked to do. Take a Range, select the contents of a block element, and call getClientRects() on it. What comes back is not the element's box. It is one rectangle per line box — one per line of text as actually laid out, after wrapping, after the font loaded, after you last resized the window.

Those rectangles are collected once, converted to document coordinates, and cached. Scrolling does not invalidate them: scrolling moves text on the screen without laying it out again, so the cache survives and the frame loop only has to subtract the scroll position. A resize does invalidate them, and so does a font arriving late, which is why a ResizeObserver and document.fonts.ready both trigger a remeasure.

Each frame, the lines currently on screen are packed into a uniform array and handed to the shader as a array<vec4f, 48> — left edge, right edge, top, bottom, all in the shader's own coordinate space. The page can be any length. Only what you can see is ever sent.

Why this way round

Line breaking is the one part of this that a shader genuinely cannot do. It depends on the font file, the hyphenation dictionary, the reader's zoom level, their minimum font size, whether a web font arrived at all. A shader has none of that and never will.

So the division of labour is the same one the rest of this repository argues for, only drawn a level finer than usual: the browser measures, the shader draws. The browser is the only thing that knows where the fifth line of this paragraph ends. The shader is the only thing that can put a convincing marker stroke there sixty times a second.

What makes it look drawn

A rectangle snapped to a line box reads as a CSS background, instantly and unmistakably. The marks here spend most of their code avoiding that:

  • The nib overshoots the start of the line, where the hand is still moving, and trails past the last glyph rather than stopping on it.
  • The stroke is taller than the line box, because a real marker covers the ascenders, and it tapers where the pen touches down and lifts.
  • The centre line wanders off the baseline, and the whole stroke sits at a slight angle that differs per line. A hand does not draw parallel to a line of type.
  • Ink runs out along the stroke, unless the line is being marked at this moment, in which case the nib is still loaded.
  • The ink multiplies the paper instead of covering it, so the fibre shows through a mark exactly as it does through a real one.

The overshoot and the lean are seeded per line, so the same line always gets the same mark, and no two lines get the same one. Nothing is random per frame; nothing crawls.

Try it

Put the pointer on a line that has not been marked yet. It inks immediately, with a fully loaded nib rather than a drying one, and the margin tick follows once the stroke is well under way.

Then resize the window. The text rewraps, every line box moves, and the marks move with them — not approximately, not one frame later, but onto the new lines, because they were never anywhere else. There is no mapping between the marks and the text to get out of step. There is only the measurement.
